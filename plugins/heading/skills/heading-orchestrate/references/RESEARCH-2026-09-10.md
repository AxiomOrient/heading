## Findings from current primary sources

1. [Managing Astra usage in Work and Codex](https://help.openai.com/en/articles/20001516-managing-usage-with-gpt-6-astra-in-work-and-codex) describes lower effort as a useful starting point and higher effort as useful for difficult problems. Higher effort can consume more allowance and does not guarantee improvement. Missing information/access cannot be repaired by reasoning. Fast mode consumes more allowance, and changing model does not restore a shared pool. This supports task-based selection, not a prohibition on starting high.
2. [Codex subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents) recommends Terra for broad/read-heavy scans and Luna for narrow, repeatable work. It identifies high with tracing complex logic/assumptions and xhigh/max with especially demanding reasoning. Child model/tool work can increase total tokens. Defaults can be configured under `[agents]`, but explicit calls override defaults and custom role files can override calls. The concurrency cap excludes the primary. These are product semantics, not Heading workload measurements.
3. [The builder's guide to GPT-5.6](https://openai.com/index/builders-guide-to-gpt-5-6/) supports Luna/Terra extraction before stronger analysis and programmatic tool filtering. Its PlayerZero example reports 64% lower inference cost, 90% lower latency, and five F1 points gained for a specific code-exploration workload. This is a vendor-published customer result, not an independent benchmark of arbitrary repositories or proof that Luna low suits all analysis.
4. [Astra model guidance](https://developers.openai.com/api/docs/guides/latest-model) advises preserving existing effective effort when migrating, except none/minimal can start at low. API configuration updates can change effort without rebuilding the prompt prefix. A skill cannot assume those API controls exist for the current native parent.
5. [Astra API model](https://developers.openai.com/api/docs/models/gpt-6-astra) documents low/medium/high/xhigh/max and long-context API pricing. [Luna](https://developers.openai.com/api/docs/models/gpt-5.6-luna) and [Terra](https://developers.openai.com/api/docs/models/gpt-5.6-terra) also expose none in the API. The current task's native spawn catalog starts at low for all three and separately exposes ultra for Astra/Terra. Host validation remains mandatory; API availability does not prove account support.
6. [OpenAI Codex spawn schema](https://github.com/openai/codex/blob/main/codex-rs/core/src/tools/handlers/multi_agents_spec.rs) documents `fork_turns` as all by default, with none or a positive turn count. The current exposed tool additionally disallows model/effort overrides on a full-history fork. A self-contained packet with none avoids accidental inherited context but does not remove fixed instructions, tool schemas, or all baseline overhead.

## Heading decision

Adopt tools first, Luna high for bounded evidence, Terra medium for broad evidence and implementation, and Astra for judgment/integration. Astra low remains the coordination default; critical/irreversible material decisions start high, and high/xhigh can be selected before the first attempt with a reason and evidence. Astra max/ultra remain budget- and host-gated exceptions. Luna xhigh/max and Terra high are authorized upfront by the user; choose them for bounded complexity or costly omissions, without repeating a low-effort attempt first. Preserve one writer, bounded handoffs, and decisive-source review.

Optimize **cost per independently accepted outcome**, with correctness as a constraint. For a candidate effort e, a useful conceptual comparison is `first-attempt cost(e) + probability of rework(e) × expected remaining repair/review cost(e)`. This is an inference framework, not an assumed retry distribution or a cost estimator. A smaller model reduces Astra usage only if its handoff avoids enough expensive rereading and repair.

The repository's `evals/route-benchmark-plan.json` compares matched cases, base revisions, tools, cache conditions, and independent acceptance. Record first-pass acceptance and all-attempt cost, latency, rework, per-model input/output/reasoning, caching, inherited context, and actual billing surface. Keep failures and blocked runs in the denominator; unknown usage is null, not zero. Reasoning tokens may already be included in output totals: never double-count. Compare upfront high/xhigh against low/medium with their actual retries included.

No production-quality or allowance-saving benchmark has been executed for this policy. Static tests and a bounded independent forward-test can verify routing behavior; they cannot certify cheapest model, correctness on all repositories, or a percentage saving.

## User-directed effort revision

The follow-up raises Luna to high by default (xhigh/max allowed) and Terra to medium (high allowed). This is a policy preference to reduce expensive rework, not a new measured model result. Official guidance permits more reasoning for complex work but does not establish lower end-to-end tokens for every task. The paired benchmark now includes Luna high/xhigh/max and Terra medium/high, retaining older lower-effort routes as historical controls. Luna max needs no additional approval under this instruction; Astra max/ultra retain their separate contracts.
